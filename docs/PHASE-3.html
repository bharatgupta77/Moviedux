backend/app/services/
collab_filter.py SVD model singleton. Wraps scikit-surprise's SVD. fit(df) trains on a ratings DataFrame. get_top_n(user_id, candidate_ids) returns predicted scores. add_rating() stores real user ratings in memory. Imported as a module-level singleton so it trains once and stays hot.
backend/app/services/
synthetic_ratings.py Cold-start seed data. Generates a pandas DataFrame of 200 fake users, each rating 30–50 movies, weighted by TMDB popularity and a random favourite genre. Called once in run.py at startup before collab_filter.fit().
backend/app/services/
gemini_client.py Groq AI client (file kept the original name for route compatibility). Two functions: get_recommendations_from_query(query, catalog) — detects intent (small talk vs movie request) and returns JSON. stream_explanation(movie, reasons) — SSE generator that yields text chunks from Groq.

backend/app/routes/
chat.py New blueprint. Two endpoints: POST /api/chat/message calls Groq and returns either a chat reply or movie results. POST /api/chat/explain streams a "Why this?" explanation via SSE using Flask's stream_with_context.
backend/app/routes/

backend/run.py Startup sequence. Loads .env first, then calls init_cache(), generate_synthetic_ratings(), and collab_filter.fit(df) — in that order — before Flask starts serving.

API Reference

New Endpoints in Phase 3

Method Path Request Response
GET /api/recommendations/collab/:userId ?n=10 {results: Movie[]}
POST /api/recommendations/ratings {user_id, movie_id, rating} {ok: true}
POST /api/chat/message {query} {type, message} or {type, reasoning, movies}
POST /api/chat/explain {movie, reasons} text/event-stream SSE
📌

The /chat/message endpoint returns a union type. If the user sends a greeting or small talk, Groq returns {type:"chat", message:"..."} — no movie search runs. If it's a real movie request, it returns {type:"movies", reasoning, recommended_ids}. This intent detection is entirely in the Groq system prompt inside gemini_client.py.

Key Patterns to Know

Things Worth Understanding Before Editing

Pattern 1 — Module-level singleton (collab_filter.py)
# At the bottom of collab_filter.py: collab_filter = CollaborativeFilter() # In run.py at startup: ratings_df = generate_synthetic_ratings() collab_filter.fit(ratings_df) # In recommendations.py routes — just import and use: from ..services.collab_filter import collab_filter collab_filter.get_top_n(user_id, candidate_ids)

The model is trained once at startup and shared across all requests. Never instantiate CollaborativeFilter() again elsewhere — import the singleton.

Pattern 2 — SSE streaming (chat.py + useChat.ts)
# Backend (Flask) yields SSE lines: yield f"data: {text}\n\n" # each chunk yield "data: [DONE]\n\n" # sentinel to close stream # Frontend (useChat.ts) reads the stream: const reader = await explainMovieRec(movie, reasons) const { done, value } = await reader.read() // parse "data: chunk\n\n" lines manually

The backend uses stream_with_context(generator) from Flask. The frontend uses the native Fetch API's response.body.getReader() — not EventSource — so it works with POST requests.

Pattern 3 — React Context (UserContext.tsx)
// Any component can access userId and ratings without prop drilling: import { useUser } from '../context/UserContext' function MyComponent() { const { userId, ratings, submitRating } = useUser() // userId — UUID, stable across refreshes // ratings — { [movieId]: 1-5 } // submitRating(movieId, stars) — saves + POSTs }

UserProvider wraps the whole app in App.tsx, so useUser() works anywhere. Both userId and ratings persist to localStorage so they survive page refreshes.

Key Decisions & Why

Why We Did It This Way

Real decisions made during Phase 3 — the reasoning, the tradeoff, and what breaks if you change them.

Decision 1 — We send the movie catalog to Groq on every chat request

Groq can only return movies that exist in the list we send it. Think of it like a restaurant menu — the waiter can only serve dishes on the menu. If a movie isn't in the list, Groq has no ID to return, and no card shows up — even if Groq knows the movie exists.

# gemini_client.py — we build a slim catalog and send it with every query slim_catalog = [{ "id": m["tmdbId"], "title": m["title"], "genre": m["genre"] } for m in catalog[:300]] # Groq picks IDs from this list → backend looks them up → returns full movie cards

Tradeoff: More movies in the list = better coverage for specific title searches, but larger token count. We settled on 300 as the balance point.

Decision 2 — Catalog: 100 movies, no overviews, lighter model

Three iterations to get here:

  • Start: 100 movies + overview[:120] — worked but limited search coverage
  • Attempt: 300 movies + overview[:60] — HTTP 413 (13,800 tokens, limit 12,000/min)
  • Fix: 300 movies, no overview — under the per-minute limit but hit 100k daily cap in ~30 searches
  • Final: 100 movies, no overview + switched to llama-3.1-8b-instant (500k tokens/day) — ~400 searches/day

Why no overview? Groq already knows what Inception, The Dark Knight etc. are about from training. We only need the ID so Groq can reference it back. The catalog is a menu of IDs, not a knowledge source.

Decision 3 — AI chat is for vibes only, not specific movie lookup

We tried adding a third intent case — if the user types a specific movie title like "Inception", return that exact card. It didn't work reliably: Groq matched by vibe instead of title and returned Tenet and other related movies instead of Inception itself.

The fix was to remove that case entirely. The search bar already does exact movie lookup perfectly. The AI chat's job is vibe/mood matching and conversation — not replacing the search bar. Two clear responsibilities, two separate tools.

# Two cases only in the system prompt: # A) Greeting/small talk → {type: "chat", message: "..."} # B) Vibe/mood/genre → {type: "movies", recommended_ids: [6-10 movies]} # # Want a specific movie? Use the search bar.

Rule of thumb for future features: before building something into AI chat, ask "does a simpler tool already do this better?" If yes, keep the boundary clean.

Decision 4 — SSE (Server-Sent Events) for streaming, not WebSocket

The "Why this?" explanation streams text word-by-word. We used SSE instead of WebSockets because SSE is one-directional (server → browser only), which is exactly what streaming text needs. WebSockets are bidirectional — great for chat apps, overkill here. SSE also works with a regular HTTP POST request, no upgrade handshake needed.

# Backend: Flask generator yields SSE lines yield f"data: {text}\n\n" # chunk yield "data: [DONE]\n\n" # sentinel # Frontend: reads with fetch() body reader, not EventSource # (EventSource only supports GET — our /explain is POST) const reader = response.body.getReader()
Decision 5 — SVD trains once at startup as a module-level singleton

The SVD model is created once in collab_filter.py as a module-level object and trained in run.py at startup. Every route just imports the singleton. We never re-instantiate it.

Why not train inside the route? SVD training takes a few seconds. If we trained on every request the app would be unusably slow. The singleton trains once, stays in memory, and serves predictions instantly. Phase 4 will add periodic retraining as real ratings accumulate.

Decision 6 — Switched from Gemini to Groq mid-phase

The original plan used Google Gemini (gemini-2.0-flash). We hit HTTP 429 errors with limit: 0 on every model — meaning the Google Cloud project had zero free tier quota allocated (not exhausted, literally zero). Creating new API keys from the same account didn't help since all keys inherit the project's quota.

Groq's free tier: 30 requests/min, 14,400/day, no credit card needed. Keys from console.groq.com work immediately. The client code in gemini_client.py kept its original filename since all routes import from it — only the internal implementation changed.

Decision 8 — SVD recommendations intentionally left off the movie detail page

The watchlist page shows two recommendation signals side by side: "Recommended For You" (TF-IDF — content similar to your saved movies) and "You Might Also Like" (SVD — what users with similar taste tend to watch). A natural next step would be to add SVD to the movie detail page too — but we deliberately didn't. Here's why.

The SVD model we built is user-based collaborative filtering. It answers: "Given this user's ratings, which movies are they most likely to enjoy?" It has no knowledge of the specific movie you are currently viewing. If you added it to the detail page, it would return the exact same list whether you're looking at Fight Club or Frozen — completely ignoring the movie context. That would feel random and broken.

# What we built — user-based SVD: # Input: user_id + all candidate movie IDs # Output: top-N movies predicted to score highly FOR THIS USER # → Correct for watchlist page (user-centric context) # → Wrong for detail page (movie-centric context) # What the detail page would need — item-based SVD: # Input: a specific movie ID # Output: movies that users who liked THIS movie also liked # → Requires item-item collaborative filtering (different model, not built yet)

The detail page already has the right tool for its context — TF-IDF "More Like This" — which finds movies with similar content (title, plot, genre, cast). That's a movie-centric signal. The watchlist page is the right place for user-centric signals.

Page Context Signal Question it answers
Detail page Movie-centric TF-IDF "More Like This" What movies are similar to this one?
Watchlist page User-centric TF-IDF "Recommended For You" What fits the content of my saved movies?
Watchlist page User-centric SVD "You Might Also Like" What do users with my taste tend to watch?
🔭

Phase 4 could add item-item collab filtering on the detail page — train a second SVD where the input is a movie ID and the output is movies that co-occur in other users' watchlists/ratings. That's a different model from what we have, and it requires enough real user data to be meaningful. For now TF-IDF content filtering covers the detail page well.

Decision 7 — Star ratings persist to localStorage, not just React state

The initial implementation stored ratings only in React state (useState<Record<number, number>>({})). Page refresh wiped them. Fix: initialize state from localStorage and write back on every rating change.

# Before: ratings lost on refresh const [ratings, setRatings] = useState({}) # After: initialized from + written back to localStorage const [ratings, setRatings] = useState(() => JSON.parse(localStorage.getItem('moviedux_ratings') ?? '{}')) # On every rating: localStorage.setItem('moviedux_ratings', JSON.stringify(next))

Same pattern as the watchlist — which already used localStorage. Ratings follow the same convention.
